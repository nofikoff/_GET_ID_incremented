# Feature Specification: Сервис выдаёт только номер

**Feature Branch**: `001-incremental-id-registry` (как пакеты 002 и 003; отдельной ветки нет)

**Created**: 2026-09-23

**Status**: Draft

**Input**: get-id выдаёт только порядковый номер. Шаблон типа ключа и отформатированное имя уходят из
сервиса: вид имени документа — конвенция репозитория-потребителя. Дизайн согласован с автором
2026-09-23 в `/brainstorming`. Номер пакета выдан get-id.

## Проблема

Сейчас у типа ключа есть шаблон вида `ADR-{number:04d}`, и сервис вместе с номером возвращает
собранное по нему имя. Имя файла документа — конвенция того репозитория, где документ лежит, а не
сервиса нумерации. Шаблон с этой конвенцией уже разошёлся: сервис выдал `ADR-0003`, а ADR и
спецификации в репозиториях именуются трёхзначным номером (`adr-003-<slug>.md`, `specs/003-<slug>/`).
Потребитель, следуя справке, брал имя из ответа сервиса как есть и получал не тот вид.

Пакет убирает из сервиса всё, что относится к виду имени. Сервис отвечает за одно: номер уникален в
паре «проект + тип» и не выдаётся дважды.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Ассистент получает номер и сам собирает имя (Priority: P1)

Ассистент в репозитории-потребителе запрашивает номер ADR, получает число 43 и создаёт
`docs/adr/adr-043-<slug>.md` по правилу из справки: номер дополняется нулями до трёх цифр.

**Why this priority**: ради этого пакет и заводится — имя документа перестаёт зависеть от настройки
сервиса.

**Independent Test**: запрос номера возвращает число и признак первой выдачи, отформатированного
имени в ответе нет; справка и описание инструмента называют трёхзначный вид.

**Acceptance Scenarios**:

1. **Given** проект с включённым типом `ADR`, **When** ассистент запрашивает номер для новой темы,
   **Then** ответ содержит номер, тему, ключ проекта, тип, признак первой выдачи и время выдачи — и
   не содержит отформатированного имени. *(FR-001)*
2. **Given** номер уже выдан, **When** ассистент повторяет запрос с той же темой, **Then** он получает
   тот же номер с признаком повтора, в том же составе полей. *(FR-001, FR-003)*
3. **Given** ассистент читает описание инструмента выдачи номера, **When** он решает, как назвать
   файл, **Then** описание говорит, что сервис выдаёт только номер, а имя собирает репозиторий:
   трёхзначный номер с ведущими нулями, `adr-043-<slug>.md` и `specs/043-<slug>/`. *(FR-004)*
4. **Given** перечень выданных номеров пары, **When** ассистент его запрашивает, **Then** каждая запись
   несёт номер, тему и время, без отформатированного имени. *(FR-001)*

---

### User Story 2 - Администратор заводит тип без шаблона (Priority: P1)

Администратор заводит новый тип ключа, указывая код, имя и описание. Поля шаблона в форме нет, и в
административном REST его тоже нет.

**Why this priority**: пока шаблон виден в консоли, администратор продолжает его настраивать и
ожидать, что сервис по нему форматирует.

**Independent Test**: форма создания и правки типа не содержит поля шаблона; тип, заведённый без
шаблона, выдаёт номера.

**Acceptance Scenarios**:

1. **Given** администратор в консоли, **When** он открывает создание или правку типа, **Then** полей
   «Шаблон» и подсказки «действует на номера, выданные после сохранения» нет. *(FR-005)*
2. **Given** запрос административного REST на заведение типа с полем шаблона, **When** он приходит,
   **Then** он отвергается как запрос с неизвестным полем, как любое другое лишнее поле. *(FR-006)*
3. **Given** тип заведён без шаблона и включён в проекте, **When** ассистент запрашивает номер,
   **Then** номер выдаётся. *(FR-005)*

---

### User Story 3 - Администратор видит номера на карточке проекта (Priority: P2)

На карточке проекта выданные номера показаны числом, темой, автором и датой. Удаление последнего
номера называет тип и номер.

**Why this priority**: карточка продолжает работать, но колонка отформатированного вида исчезает
вместе с ним.

**Independent Test**: карточка не содержит колонки «Идентификатор»; подтверждение и сообщение об
удалении называют «ADR 33».

**Acceptance Scenarios**:

1. **Given** по паре выданы номера, **When** администратор открывает карточку, **Then** у каждого видны
   номер, тема, автор и дата, колонки «Идентификатор» нет. *(FR-007)*
2. **Given** последний номер пары `ADR` — 33, **When** администратор нажимает крестик, **Then**
   подтверждение спрашивает «Удалить ADR 33?» и предупреждает, что номер может быть выдан снова;
   после удаления сообщение называет «ADR 33» и следующий номер. *(FR-008)*
3. **Given** номер не последний, **When** его пытаются удалить, **Then** отказ называет последний номер
   пары как «ADR 34». *(FR-008)*

### Edge Cases

- Номер длиннее трёх цифр (1000 и больше) — сервис отдаёт число как есть; правило трёх цифр в справке —
  минимальная ширина, больший номер пишется целиком.
- Номера, выданные до пакета с четырёхзначным видом (`ADR-0003`), — сервис хранит только число 3,
  отформатированного вида больше нет нигде; файлы, уже созданные у потребителя, пакет не трогает.
- Клиент, который ещё читает поле отформатированного имени, не находит его в ответе. Остальные поля
  ответа не меняются ни по имени, ни по смыслу.
- Тип выведен из обращения и снова возвращён — номера и счётчик пары не зависят от шаблона, которого
  больше нет.

## Requirements *(mandatory)*

### Functional Requirements

**Ответы выдачи и перечня**

- **FR-001**: Ответ выдачи номера и каждая запись перечня выданных номеров — в REST и в MCP — MUST
  содержать порядковый номер, тему в формулировке первой выдачи, ключ проекта, код типа, признак
  первой выдачи (для выдачи) и время выдачи, и MUST NOT содержать отформатированного имени.
- **FR-002**: Номер MUST отдаваться числом, без ведущих нулей и без префикса типа.
- **FR-003**: Выдача, повтор, отказы, гонка и снятие последнего номера MUST работать как до пакета:
  меняется только состав полей ответа (spec 001, spec 003).

**Справка и описание инструмента**

- **FR-004**: Страница справки (блок для `CLAUDE.md` потребителя) и описание MCP-инструмента выдачи
  номера MUST говорить: сервис выдаёт только номер; имя документа собирает репозиторий; номер
  дополняется нулями до трёх цифр — `docs/adr/adr-043-<slug>.md`, `specs/043-<slug>/`; для Spec Kit
  номер передаётся явно, и каталог, созданный не с этим номером, останавливает работу.

**Типы ключей**

- **FR-005**: Тип ключа MUST заводиться и правиться без шаблона: код, имя, описание, признак
  обращения. Поля шаблона и подсказки к нему MUST NOT быть в формах консоли.
- **FR-006**: Административный REST MUST NOT принимать и возвращать шаблон типа; поле шаблона в теле
  запроса отвергается как неизвестное по общему правилу закрытого тела.

**Консоль**

- **FR-007**: Карточка проекта MUST показывать выданные номера колонками «Тип | Номер | Ключ запроса |
  Автор | Выдан», где ключ запроса — тема, которую разработчик передал при запросе номера
  (`spec | 4 | index-only-numbers`); колонки отформатированного вида нет. Уточнено автором по снимку
  карточки 2026-09-23.
- **FR-008**: Подтверждение удаления последнего номера, сообщение об удалении, отказ «не последний» и
  запись следа удаления MUST называть номер как «код типа + номер» («ADR 33») вместо отформатированного
  вида (правка spec 003, FR-002, FR-003, FR-008).

**Хранение**

- **FR-009**: Сервис MUST NOT хранить шаблон типа и отформатированное имя выданного номера: оба
  значения удаляются из хранилища. Выданные номера, их темы, авторы и даты сохраняются.

**Правки существующего контракта**

- **FR-010**: Пакет заменяет, и при реализации MUST быть переписаны:
  - spec 001: FR-005 (отформатированный идентификатор) и FR-013a (проверка шаблона) удаляются; FR-013
    теряет шаблон; сценарии и Edge Cases про шаблон и отформатированный вид; сущность «Тип ключа»;
  - spec 002: FR-011 и FR-012, User Story 2 про шаблон, FR-013 про «отформатированный вид»,
    FR-020 про расхождение каталога с отформатированным именем;
  - spec 003: FR-002, FR-003, FR-008 и сценарии, называющие номер отформатированным видом;
  - контракты REST и MCP пакета 001 и контракт консоли пакетов 002 и 003;
  - описания хранения и примеры ответов: `data-model.md` и `quickstart.md` пакета 001,
    `data-model.md` пакета 002, `research.md` и `data-model.md` пакета 003;
  - `CLAUDE.md` — строки про фиксацию отформатированного имени;
  - решение и отвергнутые альтернативы оформляются ADR с номером из get-id.

### Key Entities

- **Тип ключа** — код, имя, описание, признак обращения. Шаблона больше нет.
- **Выданный номер** — проект, тип, тема, порядковый номер, автор, время. Отформатированного имени
  больше нет.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Ни один ответ выдачи и перечня — в REST и MCP — не содержит отформатированного имени;
  проверяется тестом на каждую поверхность.
- **SC-002**: Ассистент, следуя справке, называет ADR с номером 43 `adr-043-<slug>.md` и спецификацию
  с номером 43 `specs/043-<slug>/` — не заглядывая в настройки сервиса.
- **SC-003**: В консоли нет ни одного поля или подсказки про шаблон.
- **SC-004**: Весь набор тестов выдачи, повтора, гонки и снятия проходит; меняются только ожидания,
  проверявшие шаблон и отформатированное имя.

## Assumptions

- Потребители ответа — ассистенты, подключённые по справке; описание инструмента они читают заново в
  каждой сессии, поэтому версия API не поднимается и переходного периода с двумя форматами нет.
- Правило трёх цифр — конвенция репозиториев команды; сервис его не проверяет и не применяет.
- Отформатированные имена, выданные до пакета, не восстанавливаются: их можно собрать из номера.
- Незакоммиченные правки страницы справки автора входят в этот пакет.
- Выбор сделан автором на `/brainstorming` 2026-09-23 («мы выдаём только индекс»). Отвергнуты: сменить
  шаблон ADR на трёхзначный и оставить отформатированное имя — сервис продолжает владеть чужой
  конвенцией, и расхождение вернётся со следующим репозиторием; оставить хранимые значения без
  использования — их снова начнут читать.
