# Feature Specification: Удаление последнего выданного номера

**Feature Branch**: `001-incremental-id-registry` (как и пакет 002, ведётся в ветке 001; отдельной ветки нет)

**Created**: 2026-09-23

**Status**: Draft

**Input**: Администратор веб-консоли удаляет последний выданный номер пары «проект + тип», по одному:
крестик у последней записи в таблице «Выданные номера» карточки проекта. Дизайн согласован с автором
2026-09-23 в `/brainstorming`.

## Проблема

Сотрудники берут номер ADR или спецификации, чтобы проверить сервис, или отменяют документ сразу
после выдачи. Реестр сегодня только дописывается (spec 001, FR-004 и FR-016; spec 002, FR-013),
поэтому такой номер навсегда занимает место в нумерации, а следующий документ получает номер с
пропуском. 2026-09-23 тестовые номера на production пришлось удалять вручную в базе со сбросом
счётчика пары.

Пакет разрешает ровно одну операцию, которой раньше не было: снять с хвоста пары последний выданный
номер. Номер из середины по-прежнему неприкосновенен, поэтому дыр в нумерации не появляется.

## Clarifications

### Session 2026-09-23

- Q: Можно ли удалить последний номер пары, если проект погашен, тип выведен из обращения или пара
  выключена? → A: да, всегда — гашение останавливает выдачу новых номеров, а не управление выданными
  (FR-001).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Администратор снимает тестовые номера с хвоста (Priority: P1)

Сотрудник проверял подключение и взял два номера spec — 032 и 033. Администратор открывает карточку
проекта, удаляет 033, затем 032. Следующий запрос номера spec в этом проекте снова получает 032.

**Why this priority**: ради этого пакет и заводится; без него остаётся ручная правка production-базы.

**Independent Test**: в паре с начальным номером 31 выданы 32 и 33; администратор удаляет оба по
очереди; запрос номера с новой темой возвращает 32 и признак первой выдачи.

**Acceptance Scenarios**:

1. **Given** в паре выданы 32 и 33, **When** администратор нажимает крестик у 33 и подтверждает,
   **Then** 33 исчезает из перечня, последним выданным становится 32, следующим — 33. *(FR-001, FR-004)*
2. **Given** после этого крестик стоит у 32, **When** администратор удаляет 32, **Then** в паре нет
   выданных номеров, следующий номер — 32 (начальный 31 плюс один). *(FR-004)*
3. **Given** номер 33 с темой `test2` удалён, **When** сотрудник снова запрашивает номер с темой
   `test2`, **Then** он получает новый номер как первую выдачу, а не повтор. *(FR-006)*
4. **Given** администратор нажал крестик, **When** он отменяет подтверждение, **Then** ничего не
   удалено. *(FR-002)*

---

### User Story 2 - Номер из середины удалить нельзя (Priority: P1)

Администратор, в том числе в обход интерфейса или из устаревшей страницы, пытается удалить номер,
после которого в паре уже выдан следующий. Сервис отказывает и называет, какой номер сейчас последний.

**Why this priority**: это граница, ради которой выбрано удаление только с хвоста; её нарушение
возвращает дыры в нумерации и повторную выдачу номера из середины.

**Independent Test**: в паре выданы 5, 6, 7; прямой запрос на удаление 6 отвергается с указанием на
7; перечень и следующий номер не меняются.

**Acceptance Scenarios**:

1. **Given** в паре выданы 5, 6, 7, **When** администратор открывает карточку, **Then** крестик есть
   только у 7. *(FR-001)*
2. **Given** те же номера, **When** приходит запрос на удаление 6, **Then** он отвергается с текстом,
   называющим последний номер 7, ничего не удалено. *(FR-003)*
3. **Given** администратор открыл карточку, когда последним был 7, **When** до его нажатия сотрудник
   получил 8, а администратор удаляет 7, **Then** удаление отвергается с указанием на 8. *(FR-003, FR-005)*

---

### User Story 3 - Удаление не пересекается с выдачей (Priority: P2)

Выдача номера и удаление последнего в той же паре идут одновременно. Ни один номер не достаётся двум
темам, счётчик пары не расходится с перечнем.

**Why this priority**: гонка здесь даёт ровно то, от чего сервис защищает, — один номер у двух
документов. Проявляется редко, поэтому проверяется тестом, а не наблюдением.

**Independent Test**: параллельные процессы одновременно выдают номера и удаляют последний в одной
паре; после завершения номера в перечне идут подряд без повторов, счётчик пары равен последнему
оставшемуся номеру.

**Acceptance Scenarios**:

1. **Given** одна пара, **When** выдача и удаление стартуют одновременно, **Then** итог такой же,
   как при их выполнении по очереди в каком-то порядке. *(FR-005)*

---

### User Story 4 - Сотрудник без роли удалить не может (Priority: P1)

**Why this priority**: удаление — самая разрушительная операция консоли; закрытость справочника —
принцип III конституции.

**Independent Test**: сотрудник без роли администратора отправляет запрос удаления существующего и
несуществующего номера — оба ответа одинаковые, ничего не удалено.

**Acceptance Scenarios**:

1. **Given** сотрудник без роли администратора, **When** он отправляет запрос удаления любого номера,
   **Then** он получает тот же отказ по правам, что на остальных страницах консоли, и по ответу не
   отличить существующий номер от несуществующего. *(FR-007)*
2. **Given** администратор, **When** он запрашивает удаление номера, указав чужой проект, **Then**
   ответ «не найдено», ничего не удалено. *(FR-007)*

### Edge Cases

- Проект погашен, пара выключена или тип выведен из обращения — крестик у последнего номера есть, и
  удаление проходит как в действующей паре (FR-001).
- Начальный номер пары поднят выше выданного: выданы 1..10, начальный 50, выдан 51. Удаление 51
  возвращает последний выданный к 10, но следующим остаётся 51 — начальный номер не откатывается.
  Удаление 10 после этого разрешено, следующий номер по-прежнему 51.
- Удалён последний номер пары, в которой начальный номер выше всех выданных — последним выданным
  считается 0, следующий номер — начальный плюс один.
- Удаление после поднятия начального номера не нарушает правило spec 001, FR-014b: начальный номер
  по-прежнему не ниже максимального выданного, потому что максимум только уменьшился.
- Двойной клик, повтор запроса на уже удалённый номер или два администратора, одновременно снимающих
  один номер, — одно снятие проходит, остальные получают «не найдено», второй номер не снимается.
- Номер чужого проекта и несуществующий номер администратор видит одинаково — «не найдено»: различать
  их незачем, оба означают устаревшую или подделанную ссылку.
- Удалённый номер мог уже попасть в commit потребителя. Сервис этого не видит; подтверждение
  предупреждает, что номер может быть выдан снова другой теме.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Администратор MUST иметь возможность удалить в веб-консоли последний выданный номер
  пары «проект + тип» — наибольший номер среди оставшихся в паре. Действие MUST быть доступно только у
  этой записи; повторное удаление снимает следующий номер с хвоста. Статус проекта, типа и пары на
  удаление MUST NOT влиять: погашенный проект, выведенный тип и выключенная пара удаляются так же.
  Перечень идёт от новых к старым, поэтому действие стоит только в первой строке первой страницы пары;
  на остальных страницах и у пары без номеров его нет.
- **FR-002**: Удаление MUST требовать подтверждения, в котором назван отформатированный вид номера и
  сказано, что номер может быть выдан снова. Без подтверждения ничего не удаляется.
- **FR-003**: Запрос на удаление номера, который не последний в своей паре, MUST отвергаться
  независимо от того, как он отправлен. Отказ MUST называть номер, который сейчас последний; ничего
  не удаляется.
- **FR-004**: После удаления последним выданным номером пары MUST становиться наибольший из оставшихся
  номеров, а при их отсутствии — 0. Следующий номер считается по прежнему правилу spec 001, FR-014a:
  больший из начального и последнего выданного плюс один. Новое значение берётся из оставшихся
  записей, а не вычитанием единицы, поэтому счётчик, разошедшийся с перечнем (например, после ручной
  правки базы), после снятия с ним снова совпадает.
- **FR-005**: Удаление и выдача номера в одной паре MUST NOT выполняться одновременно: результат MUST
  совпадать с их выполнением по очереди. Разные пары друг друга не ждут.
- **FR-006**: Удалённая запись MUST исчезать из реестра полностью: её тема перестаёт быть занятой, и
  повтор этой темы выдаёт номер как первую выдачу.
- **FR-007**: Удаление MUST быть доступно только администратору; отказ сотруднику без роли MUST быть
  одинаковым для существующего и несуществующего номера (spec 002, FR-016). Номер, не принадлежащий
  указанному проекту, MUST давать «не найдено». Операция MUST быть защищена от межсайтовой подделки
  запроса (spec 002, FR-017).
- **FR-008**: Каждое удаление MUST оставлять запись в журнале приложения тем же механизмом, что
  изменения справочника (spec 002, FR-019): администратор, проект, тип, номер, его отформатированный
  вид и тема, новое значение последнего выданного. Сбой записи MUST NOT отменять удаление и MUST NOT
  показываться администратору как отказ.
- **FR-009**: Любой другой путь изменения или удаления записи реестра через модель выданного номера —
  изменение, массовое удаление, удаление через связь с проектом — MUST оставаться закрытым: это
  удаление — единственная санкционированная операция над выданным номером. Прямые запросы к таблице в
  обход модели остаются открытыми, как и сейчас: ими чистит только тестовый набор гонок.
- **FR-010**: Удаление MUST NOT появляться в MCP и в административном REST (ADR-002 закрывает MCP;
  REST — по объёму этого пакета). Поведение выдачи, повтора и просмотра в REST и MCP MUST NOT
  меняться.

**Правки существующего контракта**

- **FR-011**: Этот пакет заменяет следующие формулировки, и при реализации они MUST быть переписаны:
  - spec 001, FR-004 — номер не выдаётся повторно, кроме номера, удалённого администратором с хвоста
    пары (этот пакет);
  - spec 001, FR-002 — повтор темы возвращает выданный номер, пока запись этой темы не снята;
  - spec 001, FR-016 — записи реестра не удаляются, кроме той же операции;
  - spec 001, FR-001 не меняется: снятие только с хвоста пропусков не создаёт;
  - spec 002, FR-013 — просмотр не даёт изменить запись реестра, удалить можно только последнюю по
    этому пакету;
  - преамбула, принципы I и II конституции и `CLAUDE.md` §Выдача номера — «номер не переиспользуется
    никогда» становится «переиспользуется только номер, снятый администратором с хвоста пары», повтор
    действует, пока запись темы существует. Поправка — MAJOR по Governance конституции (2.0.0),
    отдельным commit; утверждает автор репозитория;
  - описание модели выданного номера в коде, которое называет записи неудаляемыми;
  - решение и отвергнутые альтернативы оформляются ADR, номер которого выдаёт get-id.

### Key Entities

Новых сущностей нет. Операция меняет две существующие сущности spec 001: выданный идентификатор
(запись удаляется) и включение типа в проекте (последний выданный номер уменьшается).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Два тестовых номера на хвосте пары снимаются двумя подтверждёнными нажатиями на карточке
  проекта, после чего следующий выданный номер равен первому снятому.
- **SC-002**: Ни один номер, после которого в паре выдан следующий, не удаляется — ни из интерфейса,
  ни прямым запросом; проверяется тестом на каждый путь.
- **SC-003**: Под параллельной нагрузкой выдачи и удаления в одной паре итоговый перечень номеров
  идёт подряд, без повторов, и последний выданный номер пары равен наибольшему в перечне.
- **SC-004**: Весь существующий набор тестов выдачи, повтора, REST и MCP проходит без изменений в
  ожиданиях, кроме тестов, проверяющих прежний запрет на удаление.
- **SC-005**: Ручная правка базы для удаления номера больше не требуется.

## Assumptions

- Удаление — редкая служебная операция единиц администраторов; отдельной истории удалённых номеров
  сверх записи в журнале приложения не ведётся.
- Удаляется один номер за действие; массового удаления и удаления по фильтру нет.
- Удалённый номер может уже упоминаться в репозитории потребителя; ответственность за решение удалить
  такой номер несёт администратор, сервис ссылок не проверяет.
- Журнал обращений `/admin/logs` в объём не входит.
- Выбор «только с хвоста» сделан автором на `/brainstorming` 2026-09-23. Отвергнуты: удаление любого
  номера со сдвигом счётчика до максимума оставшихся — появляются дыры, и номер из середины уже не
  вернуть; удаление без отката счётчика — тестовые номера сжигают нумерацию; мягкое снятие с пометкой
  — перечень не очищается.
