# Feature Specification: Веб-консоль администратора

**Feature Branch**: `001-incremental-id-registry` (пакет ведётся в ветке 001 по решению автора; отдельной ветки нет)

**Created**: 2026-09-23

**Status**: Implemented

**Input**: Веб-консоль администратора get-id поверх реализованного пакета 001: справочники проектов и
типов ключей редактируются в браузере, а не только через REST; администратору видны выданные номера
и журнал обращений. Дизайн согласован с автором 2026-09-23 в `/brainstorming`.

## Проблема

Справочники проектов и типов ключей сегодня меняются только через административный REST: чтобы
завести проект, администратор пишет curl-запрос с токеном. Веб-экраны «Проекты» и «Типы ключей»
лишь показывают списки. Выданные номера и журнал обращений в браузере не видны вовсе.

Пакет 001 изначально предполагал администрирование справочников в веб-интерфейсе (spec 001,
Assumptions: «вход, страница токена и администрирование справочников»), но задачи T069 и T070 сузили
экраны до списков. Этот пакет закрывает разрыв и не меняет ни одного правила выдачи.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Администратор заводит проект в браузере (Priority: P1)

Администратор открывает консоль, заводит проект по адресу репозитория, включает в нём типы ключей и
указывает уже занятые номера. После этого ассистенты команды получают номера через MCP — без единого
curl-запроса.

**Why this priority**: без этого каждый новый репозиторий требует ручного обращения к API, а это
главная причина, по которой консоль заводится.

**Independent Test**: на пустом справочнике администратор в браузере заводит проект, включает `ADR`
с последним занятым номером 12; запрос номера для этого проекта возвращает 13.

**Acceptance Scenarios**:

1. **Given** администратор в консоли, **When** он отправляет форму нового проекта с адресом
   `git@gitlab.cas.ai:team/backend.git` и именем, **Then** проект появляется в списке с ключом
   `gitlab.cas.ai/team/backend`, выведенным из адреса. *(FR-001, FR-002)*
2. **Given** проект с тем же репозиторием уже заведён под другой формой адреса, **When** администратор
   отправляет форму, **Then** форма возвращается с ошибкой под полем адреса и введёнными значениями,
   второй проект не появляется. *(FR-003)*
3. **Given** проект заведён, **When** администратор на карточке проекта отмечает `ADR` с seed 12 и
   `spec` без seed и сохраняет, **Then** обе пары включены, карточка показывает следующий номер 13 для
   `ADR` и 1 для `spec`. *(FR-006, FR-007)*
4. **Given** по `ADR` уже выданы номера до 20, **When** администратор задаёт seed 5, **Then** форма
   возвращается с ошибкой под полем seed этого типа, набор не меняется. *(FR-008)*
5. **Given** `ADR` включён, **When** администратор снимает его галочку и подтверждает отправку,
   **Then** пара выключена, её счётчик сохранён; без подтверждения набор не меняется. *(FR-009)*

---

### User Story 2 - Администратор ведёт справочник типов (Priority: P2)

Администратор заводит новый род документа (например, `RFC` с шаблоном `RFC-{number:03d}`), правит имя
или шаблон существующего типа и выводит тип из обращения.

**Why this priority**: типы меняются редко — два стандартных типа засеяны при установке. Но без формы
новый род документа снова требует curl.

**Independent Test**: администратор заводит `RFC` с шаблоном без плейсхолдера номера — получает
ошибку под полем шаблона; с правильным шаблоном тип появляется в списке и доступен для включения на
карточке проекта.

**Acceptance Scenarios**:

1. **Given** администратор в консоли, **When** он заводит тип с шаблоном `RFC-{name}`, **Then** форма
   возвращается с ошибкой под полем шаблона: нет номера. *(FR-011)*
2. **Given** по типу выдан номер `ADR-0007`, **When** администратор меняет шаблон на `ADR-{number:03d}`,
   **Then** в перечне и при повторе номер 7 остаётся `ADR-0007`, а следующая выдача получает новый вид.
   *(FR-012)*
3. **Given** тип выведен из обращения, **When** администратор открывает карточку проекта, **Then**
   включить этот тип там нельзя. *(FR-010)*

---

### User Story 3 - Администратор видит выданные номера (Priority: P3)

На карточке проекта администратор видит, какие номера выданы по каждому типу, кем, когда и с какой
темой.

**Why this priority**: сейчас выданное видно только через REST или ассистента. Для разбора «кто взял
номер 42» нужен просмотр, но выдача работает и без него.

**Independent Test**: после трёх выдач по `ADR` карточка проекта показывает три строки от новой к
старой с формулировкой первой выдачи, автором и датой.

**Acceptance Scenarios**:

1. **Given** по паре выдано 60 номеров, **When** администратор открывает карточку, **Then** он видит
   номера от новых к старым постранично, по каждому — номер, отформатированный вид, тему в формулировке
   первой выдачи, автора и дату. *(FR-013)*
2. **Given** тип был выключен после выдач, **When** администратор открывает карточку, **Then** номера
   этого типа по-прежнему видны. *(FR-013)*

---

### User Story 4 - Администратор разбирает журнал обращений (Priority: P4)

Администратор открывает журнал и отфильтровывает обращения одного сотрудника за период, отдельно по
REST или MCP, и раскрывает параметры конкретного запроса.

**Why this priority**: журнал нужен для разбора инцидентов и вопросов «почему у меня отказ», это
редкая операция.

**Independent Test**: после обращений двух сотрудников фильтр по одному из них за сегодня показывает
только его записи; ссылка с фильтром, открытая заново, показывает тот же результат.

**Acceptance Scenarios**:

1. **Given** в журнале записи двух сотрудников за три дня, **When** администратор выбирает одного
   сотрудника и один день, **Then** видны только записи этого сотрудника за этот день, от новых к
   старым. *(FR-014, FR-015)*
2. **Given** отфильтрованный журнал, **When** администратор копирует адрес страницы и открывает его
   снова, **Then** фильтр и результат те же. *(FR-015)*
3. **Given** запись с параметрами запроса, **When** администратор раскрывает её, **Then** он видит
   параметры, как они сохранены в журнале. *(FR-014)*

---

### User Story 5 - Обычный сотрудник консоли не видит (Priority: P1)

Сотрудник без роли администратора не получает ни экранов, ни форм консоли и по ответу не может
определить, существует ли проект или тип с данным идентификатором.

**Why this priority**: закрытость справочника — принцип III конституции; нарушение раскрывает перечень
проектов.

**Independent Test**: сотрудник открывает каждую страницу консоли и отправляет каждую форму, в том
числе с несуществующим идентификатором, — везде одинаковый отказ по правам, ничего не изменено.

**Acceptance Scenarios**:

1. **Given** сотрудник без роли администратора, **When** он открывает любую страницу консоли или
   отправляет любую её форму, **Then** он получает отказ по правам, справочник не меняется. *(FR-016)*
2. **Given** тот же сотрудник, **When** он обращается к карточке с несуществующим идентификатором,
   **Then** ответ тот же, что для существующего. *(FR-016)*

### Edge Cases

- Проект погашен — на карточке видны реквизиты, типы и выданные номера; выдача новых номеров
  отвергается сервисом как прежде, форма типов остаётся доступной.
- Проект возвращён в обращение — выдача продолжается с прежних счётчиков.
- Администратор снимает все галочки типов — все пары выключены, счётчики сохранены.
- Тип выведен из обращения, пока администратор держит открытой форму проекта с его галочкой —
  отправка отвергается с ошибкой под полем этого типа, набор не меняется.
- Два администратора одновременно заводят проект по одному репозиторию — один успешен, второй
  получает ту же ошибку под полем адреса, что и при обычном дубле.
- Форма отправлена без действующего CSRF-токена (истёкшая страница) — запрос отвергается, ничего не
  меняется, администратор видит, что страницу нужно обновить.
- Журнал пуст за выбранный период — показано явное «записей нет», а не пустая таблица.
- Тип выведен из обращения глобально, но включён в проекте с прошлого раза — на карточке он виден
  строкой без галочки с пометкой «выведен из обращения, будет выключен при сохранении»; сохранение
  набора выключает эту пару (включить погашенный тип нельзя, FR-010), и она попадает в перечень
  подтверждения FR-009. Выдачу это не меняет: по погашенному типу она уже закрыта.
- Фильтр журнала с датой «с» позже даты «по» — ошибка под полем даты, а не пустой результат.

## Requirements *(mandatory)*

### Functional Requirements

**Проекты**

- **FR-001**: Администратор MUST иметь возможность завести проект в веб-консоли, указав адрес
  репозитория, человекочитаемое имя и необязательное описание.
- **FR-002**: Ключ проекта MUST выводиться из адреса по правилу spec 001 (FR-008) и MUST NOT
  вводиться вручную.
- **FR-003**: Повторная регистрация того же репозитория под любой формой адреса, как и неразбираемый
  адрес, MUST возвращать форму с ошибкой под полем адреса, сохранёнными введёнными значениями и тем же
  текстом отказа, что даёт административный REST.
- **FR-004**: Администратор MUST иметь возможность изменить имя и описание проекта, вывести проект из
  обращения и вернуть его. Адрес и ключ после заведения MUST NOT меняться. Удаления проекта нет
  (spec 001, FR-016). Вывод из обращения MUST требовать подтверждения: он останавливает выдачу по
  всем типам проекта. Возврат в обращение подтверждения не требует — он ничего не останавливает.
- **FR-005**: Список проектов MUST показывать ключ, имя и признак обращения каждого проекта, включая
  погашенные; карточка проекта MUST показывать его реквизиты, типы и выданные номера.

**Типы в проекте**

- **FR-006**: Карточка проекта MUST показывать все активные типы справочника, для каждого — включён ли
  он в проекте, начальное значение, последний выданный номер и следующий номер. У проекта без единой
  пары типов форма MUST показывать каждый активный тип уже отмеченным — сравнивать отметку не с чем,
  а не отмечать ни одного значило бы предлагать пустой набор для только что заведённого проекта.
- **FR-007**: Администратор MUST иметь возможность одной отправкой задать набор включённых типов и
  начальные значения. Тип без указанного начального значения сохраняет текущее; у новой пары оно равно
  0 (spec 001, FR-014a).
- **FR-008**: Начальное значение ниже последнего выданного MUST возвращать форму с ошибкой под полем
  этого типа; набор при этом MUST NOT меняться (spec 001, FR-014b). Начальное значение, указанное для
  типа без отметки, MUST возвращать ошибку под тем же полем («Отметьте тип, чтобы задать начальный
  номер.») вместо того, чтобы тихо отбрасываться вместе с остальным полем — молчаливая отбраковка на
  продакшене выглядела как успешное сохранение, которое ничего не сохранило.
- **FR-009**: Тип, снятый с отметки, MUST выключаться в проекте с сохранением счётчика (spec 001,
  FR-016). Если отправка снимает отметку хотя бы с одного включённого типа, она MUST требовать
  подтверждения с перечнем этих типов: выдача по ним остановится. Отправка, после которой ни одна пара
  не создана и ни у одной не изменились `is_enabled` или `seed_sequence`, MUST давать flash «Изменений
  нет.» вместо «Набор типов проекта сохранён.».
- **FR-010**: Тип, выведенный из обращения, MUST NOT включаться в проекте; попытка, в том числе
  через устаревшую форму, MUST возвращать ошибку под полем этого типа.

**Типы ключей**

- **FR-011**: Администратор MUST иметь возможность завести тип ключа с кодом, именем, шаблоном и
  необязательным описанием, изменить имя, шаблон и описание, вывести тип из обращения и вернуть его.
  Код после заведения MUST NOT меняться. Шаблон проверяется при сохранении по правилу spec 001
  (FR-013a), ошибка приходит под полем шаблона. Вывод типа из обращения MUST требовать
  подтверждения: он останавливает выдачу по этому типу во всех проектах.
- **FR-012**: Правка шаблона MUST NOT менять отформатированный вид уже выданных номеров (spec 001,
  FR-005).

**Просмотр**

- **FR-013**: Карточка проекта MUST показывать выданные номера по каждой паре, в том числе по
  выключенным типам: номер, отформатированный вид, тему в формулировке первой выдачи, автора и дату —
  от новых к старым, по 50 на страницу для каждой пары. Просмотр MUST NOT давать изменить или удалить запись реестра.
- **FR-014**: Экран журнала MUST показывать записи журнала обращений от новых к старым: дату,
  сотрудника, имя токена, метод и путь, код ответа, длительность; параметры запроса — по раскрытию
  записи. Параметры показываются как сохранены: заголовок авторизации и значение токена в журнал не
  попадают (spec 001, FR-025), формулировки тем видит только администратор.
- **FR-015**: Журнал MUST фильтроваться по сотруднику, диапазону дат и поверхности (REST или MCP).
  Даты — календарные дни в часовом поясе сервиса, обе границы включительно. Поверхность определяется
  по адресу обращения: `/mcp` — MCP, `/api/` — REST. В списке сотрудников — все, чьи записи могут быть
  в журнале, включая деактивированных. Дата «по» раньше даты «с» и несуществующий сотрудник — ошибка
  под соответствующим полем фильтра. Фильтр MUST быть частью адреса страницы, так что ссылка
  воспроизводит тот же результат. Записи выводятся постранично, по 50.

**Доступ и совместимость**

- **FR-016**: Каждая страница и каждая форма консоли, включая просмотр номеров и журнала, MUST быть
  доступна только администратору. Отказ сотруднику без роли MUST быть одинаковым для существующего и
  несуществующего идентификатора (spec 001, FR-017). Гость отправляется на страницу входа. Роль
  проверяется на каждом запросе, поэтому администратор, у которого роль сняли консольной командой,
  получает отказ со следующего запроса той же сессии.
- **FR-017**: Каждая форма консоли MUST быть защищена от межсайтовой подделки запроса.
- **FR-018**: Каждая операция, которую выполняет административный REST, MUST выполняться в консоли
  с теми же правилами и теми же формулировками отказов. Поведение REST и MCP MUST NOT меняться.
- **FR-019**: Каждое изменение справочника — через консоль или через административный REST — MUST
  оставлять запись в журнале приложения: кто из администраторов, какая операция, над какой сущностью и
  какие поля изменились («было → стало»). Запись делается после изменения; её сбой MUST NOT отменять
  изменение (как сбой журнала обращений в spec 001, FR-026). Секретов в записи нет — их в справочнике
  нет.

**Справка**

- **FR-020**: Любой вошедший сотрудник, не только администратор, MUST иметь доступ к странице справки
  с командой подключения Claude Code к MCP-серверу — адрес сервера MUST браться из конфигурации
  приложения, не быть зашит строкой — и со ссылкой на кабинет токенов, где токен заводится и
  показывается один раз. Страница MUST перечислять доступные MCP-инструменты. Гость отправляется на
  страницу входа, как с любой другой закрытой страницы.

### Key Entities

Новых сущностей нет. Консоль работает с сущностями spec 001: проект, тип ключа, включение типа в
проекте (со счётчиком), выданный идентификатор, запись журнала обращений, пользователь.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Администратор заводит проект, включает в нём два типа с начальными значениями и
  убеждается в следующем номере — не открывая терминал и не создавая токен, за время не больше
  двух минут.
- **SC-002**: Для каждой операции административного REST существует путь в консоли, дающий тот же
  результат и тот же текст отказа на тех же входных данных — проверяется попарным тестом.
- **SC-003**: Весь существующий набор тестов REST и MCP проходит без изменений в ожиданиях.
- **SC-004**: Обращения одного сотрудника за выбранный день находятся одним фильтром, и ссылка на
  отфильтрованную страницу воспроизводит тот же результат.
- **SC-005**: Сотрудник без роли администратора не получает ни одной страницы или формы консоли и не
  может отличить существующий идентификатор от несуществующего.

## Assumptions

- Администраторы — единицы человек; объём справочника — десятки проектов и типов, журнал хранится
  90 дней (spec 001). Производительность просмотра не проектируется отдельно.
- Консоль — служебный интерфейс, не продукт: минимальная вёрстка без сборки фронтенда, в стиле
  существующих экранов.
- Управление пользователями и ролями в вебе вне объёма: роли и деактивация остаются консольными
  командами (spec 001, FR-021).
- Административных инструментов в MCP нет и не появляется (ADR-002); меняется лишь следствие ADR-002
  о том, что веб-экраны только показывают справочник.
- Пакет ведётся в ветке `001-incremental-id-registry` и выкладывается вместе с ней.
- Способ переиспользования правил между REST и вебом выбран на `/brainstorming` 2026-09-23: общий
  прикладной слой операций и одно место правил валидации для двух транспортов. Отвергнуты:
  веб-запросы как наследники REST-запросов (закрытое тело REST отвергает служебные поля формы) и
  компонентный фронтенд со сборкой (на хосте нет инструментов сборки, объём форм не оправдывает).
