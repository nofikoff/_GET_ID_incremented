# Feature Specification: Реестр инкрементальных идентификаторов

**Feature Branch**: `001-incremental-id-registry`

**Created**: 2026-09-20

**Status**: Draft

**Input**: Техническое задание на микросервис выдачи ID для ADR и спецификаций, дополненное
требованиями администрируемого справочника проектов и доступа AI-ассистентов через MCP.

## Проблема

Номер следующего ADR или спецификации сегодня определяется листингом каталога в репозитории. Два
человека или два AI-агента, работающие одновременно, видят одинаковый листинг и берут один и тот же
номер. Конфликт всплывает на merge — когда оба документа уже написаны, а на их номера уже сослались
соседние документы.

Сервис делает выдачу номера атомарной и централизованной: номер закрепляется за документом в момент
запроса, а не в момент коммита.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Выдача номера без гонки (Priority: P1)

Разработчик или AI-агент собирается завести новый ADR в репозитории. Он называет сервису проект, тип
ключа и тему документа и получает номер, который гарантированно не занят и не будет выдан другому.
Если запрос повторяется — из-за оборванного соединения, перезапуска агента или просто второй раз —
возвращается тот же самый номер, а не следующий.

**Why this priority**: это единственная причина, по которой сервис существует. Всё остальное
обслуживает этот сценарий.

**Independent Test**: на заполненном справочнике выполнить два одновременных запроса номера и
убедиться, что номера разные; затем повторить один из запросов и убедиться, что номер тот же.

**Acceptance Scenarios**:

1. **Given** проект зарегистрирован и тип ключа в нём включён, номеров ещё не выдавалось,
   **When** клиент запрашивает номер для темы `add-oauth-auth`,
   **Then** он получает номер 1, отформатированный идентификатор по шаблону типа и признак первой
   выдачи.
2. **Given** для темы `add-oauth-auth` номер 1 уже выдан,
   **When** клиент запрашивает номер для той же тройки «проект + тип + тема»,
   **Then** он получает тот же номер 1 и признак того, что выдача не новая, и в реестре не
   появляется второй записи.
3. **Given** проект зарегистрирован и тип включён,
   **When** два клиента одновременно запрашивают номер для разных тем,
   **Then** оба запроса завершаются успешно и получают разные последовательные номера.
4. **Given** для пары «проект + тип» выдано несколько номеров,
   **When** клиент запрашивает список выданных,
   **Then** он получает все записи от новых к старым с темой и датой выдачи.

### User Story 2 - Администратор ведёт справочники (Priority: P2)

Администратор регистрирует репозиторий как проект, заводит типы ключей и указывает, какие типы
доступны в каком проекте. Обычный пользователь ничего из этого не видит и не меняет — он вообще не
получает перечня проектов.

**Why this priority**: без заполненного справочника первый сценарий не работает ни в одном новом
репозитории. Но справочник имеет смысл только вместе с выдачей, поэтому он второй, а не первый.

**Independent Test**: администратор заводит проект и тип, включает тип в проекте, затем читает
список проектов; пользователь без роли администратора получает отказ на тех же операциях.

**Acceptance Scenarios**:

1. **Given** администратор аутентифицирован,
   **When** он регистрирует проект, указывая адрес репозитория,
   **Then** проект появляется в справочнике с нормализованным ключом, выведенным из этого адреса.
2. **Given** администратор зарегистрировал тип ключа с шаблоном форматирования,
   **When** он включает этот тип в проекте,
   **Then** запросы номера этого типа в этом проекте начинают обслуживаться, начиная с номера 1.
3. **Given** пользователь без роли администратора аутентифицирован,
   **When** он обращается к любой операции справочника — чтение перечня, создание, изменение,
   **Then** он получает отказ по правам, и перечень проектов ему не раскрывается.
4. **Given** проект выведен из обращения,
   **When** клиент запрашивает для него новый номер,
   **Then** запрос отвергается, а ранее выданные номера продолжают читаться.

### User Story 3 - Вход сотрудника и получение токена (Priority: P3)

Сотрудник входит в веб-интерфейс сервиса через корпоративный Google-аккаунт и получает токен для
программного доступа. Токен он может пересоздать и отозвать сам.

**Why this priority**: без токена ни REST, ни MCP не работают для реального человека, но в тестах
сценарии 1 и 2 проверяются независимо от способа входа.

**Independent Test**: вход аккаунтом корпоративного домена завершается созданием пользователя и
выдачей токена; вход аккаунтом постороннего домена отвергается.

**Acceptance Scenarios**:

1. **Given** сотрудник с почтой корпоративного домена,
   **When** он входит через Google,
   **Then** он попадает в личный кабинет и может создать токен.
2. **Given** пользователь с почтой постороннего домена,
   **When** он входит через Google,
   **Then** доступ отвергается и учётная запись не создаётся.
3. **Given** у пользователя есть действующий токен,
   **When** он отзывает токен,
   **Then** запросы с этим токеном перестают обслуживаться немедленно.

### User Story 4 - AI-ассистент работает через MCP (Priority: P4)

AI-ассистент подключается к сервису как к MCP-серверу и получает номер, не спрашивая человека о
ключе проекта: он сам читает адрес origin локального репозитория и передаёт его сервису.

**Why this priority**: это основной способ потребления сервиса в повседневной работе, но он
надстраивается над уже работающей выдачей и аутентификацией.

**Independent Test**: подключить MCP-сервер клиентом, вызвать инструмент определения проекта по
адресу репозитория, затем инструмент выдачи номера — без ручного ввода ключа проекта.

**Acceptance Scenarios**:

1. **Given** MCP-сервер подключён с действующим токеном,
   **When** ассистент передаёт адрес origin незарегистрированного репозитория,
   **Then** он получает нормализованный ключ, признак «не зарегистрирован» и указание обратиться к
   администратору — и не пытается выдать номер.
2. **Given** адрес origin принадлежит зарегистрированному проекту,
   **When** ассистент запрашивает определение проекта,
   **Then** он получает ключ проекта и перечень включённых в нём типов ключей.
3. **Given** ассистент получил ключ проекта,
   **When** он запрашивает номер,
   **Then** результат совпадает с тем, что вернул бы тот же запрос через REST — вплоть до номера и
   признака новизны.

---

### User Story 5 - Журнал обращений (Priority: P5)

Администратор может восстановить, кто и когда запрашивал номера: каждое обращение к API
записывается.

**Why this priority**: нужен для разбора спорных ситуаций, но ни один пользовательский сценарий на
него не опирается.

**Independent Test**: выполнить обращение к API и убедиться, что запись журнала содержит
пользователя, endpoint, параметры, адрес, код ответа и длительность.

**Acceptance Scenarios**:

1. **Given** клиент аутентифицирован,
   **When** он обращается к любому endpoint API,
   **Then** в журнале появляется запись с пользователем, адресом, параметрами и кодом ответа.
2. **Given** запись в журнал не может быть выполнена,
   **When** клиент запросил номер и номер выдан,
   **Then** клиент получает номер, а не ошибку.

### Edge Cases

- Адрес origin пришёл в SSH-форме, в HTTPS-форме, с портом, с суффиксом `.git`, в другом регистре —
  все формы одного репозитория дают один ключ проекта.
- Адрес origin не разбирается как адрес репозитория — запрос отвергается с указанием, что именно не
  разобрано, а не молча считает строку ключом.
- Тип ключа выключен в проекте после того, как по нему уже выдавались номера — новые номера не
  выдаются, ранее выданные читаются, нумерация при повторном включении продолжается с прежнего
  места, а не с единицы.
- Тип ключа выведен из обращения глобально — он не может быть включён ни в одном проекте.
- Порядковый номер превысил ширину, заложенную в шаблон форматирования — идентификатор печатается
  целиком, без усечения.
- Тема документа передана пустой или состоящей из пробелов — запрос отвергается.
- Токен отозван между двумя запросами агента — второй запрос отвергается, ранее выданный номер
  остаётся в реестре.
- Одновременные запросы для одной пары «проект + тип» с одинаковой темой — обоим возвращается один
  и тот же номер, дубликат в реестре не создаётся.

## Requirements *(mandatory)*

### Functional Requirements

**Выдача номеров**

- **FR-001**: Система MUST выдавать порядковые номера, уникальные в пределах пары «проект + тип
  ключа», начиная с 1 и без пропусков в нормальной работе.
- **FR-002**: Система MUST возвращать ранее выданный номер при повторном запросе с той же тройкой
  «проект + тип ключа + тема документа» и MUST различать в ответе первую выдачу и повтор.
- **FR-003**: Система MUST обслуживать одновременные запросы номера для одной пары «проект + тип»
  так, что каждый запрос получает собственный номер и ни один не завершается ошибкой конкуренции,
  видимой клиенту.
- **FR-004**: Система MUST NOT выдавать номер повторно ни при каких условиях, включая удаление
  документа на стороне потребителя.
- **FR-005**: Система MUST возвращать вместе с номером отформатированный идентификатор, построенный
  по шаблону, заданному типом ключа.
- **FR-006**: Система MUST отдавать перечень выданных идентификаторов для пары «проект + тип» в
  порядке убывания номера, с темой документа и датой выдачи.
- **FR-007**: Сравнение темы документа для целей повторной выдачи MUST выполняться по
  нормализованному виду [NEEDS CLARIFICATION: считать ли `add-oauth-auth`, `Add OAuth Auth` и
  `add oauth auth` одной темой — нормализация регистра и разделителей, или требовать точного
  совпадения строки?].

**Ключ проекта**

- **FR-008**: Система MUST выводить ключ проекта из адреса репозитория детерминированной
  нормализацией: снимаются протокол, имя пользователя, порт, суффикс `.git`, регистр приводится к
  нижнему.
- **FR-009**: Система MUST предоставлять операцию, которая по переданному адресу репозитория
  возвращает нормализованный ключ, признак регистрации проекта и перечень включённых в нём типов
  ключей — и MUST NOT раскрывать в этой операции никакие другие проекты.
- **FR-010**: Система MUST отвергать запрос номера для незарегистрированного ключа проекта и MUST
  включать в ответ нормализованный ключ и указание обратиться к администратору.
- **FR-011**: Система MUST NOT регистрировать проект автоматически по факту обращения к нему.

**Справочники**

- **FR-012**: Система MUST позволять администратору регистрировать проект, изменять его
  человекочитаемое имя и выводить проект из обращения.
- **FR-013**: Система MUST позволять администратору заводить тип ключа с кодом, именем и шаблоном
  форматирования идентификатора и выводить тип из обращения.
- **FR-014**: Типы ключей MUST быть общими для всех проектов; администратор MUST указывать, какие
  типы включены в каждом проекте, а нумерация MUST вестись отдельно в каждой паре «проект + тип».
- **FR-015**: Система MUST отвергать запрос номера для типа, не включённого в данном проекте, или
  для проекта либо типа, выведенного из обращения.
- **FR-016**: Система MUST NOT удалять проекты, типы ключей и записи реестра выданных номеров;
  вывод из обращения MUST выполняться признаком активности.
- **FR-017**: Перечень проектов и перечень типов ключей MUST быть доступны только администратору.

**Доступ**

- **FR-018**: Система MUST аутентифицировать людей через Google и MUST допускать только учётные
  записи корпоративного домена `@cas.ai`, отвергая остальные без создания учётной записи.
- **FR-019**: Система MUST выдавать аутентифицированному пользователю долгоживущий токен для
  программного доступа и MUST позволять пересоздать и отозвать его; отзыв MUST действовать
  немедленно.
- **FR-020**: Все операции над реестром и справочниками MUST требовать действующего токена.
- **FR-021**: Роль администратора MUST назначаться администратором; первый администратор MUST
  подниматься из конфигурации развёртывания.

**Доступ AI-ассистентов**

- **FR-022**: Система MUST предоставлять MCP-сервер, авторизуемый тем же токеном, что и остальной
  API, с инструментами определения проекта по адресу репозитория, выдачи номера и чтения перечня
  выданных.
- **FR-023**: Описание инструмента определения проекта MUST явно сообщать, что адрес origin читает
  клиент на своей стороне и передаёт его в запросе — сервер к локальному репозиторию доступа не
  имеет.
- **FR-024**: Результат операции через MCP MUST совпадать с результатом той же операции через REST
  при тех же входных данных.

**Журнал**

- **FR-025**: Система MUST записывать каждое обращение к API: пользователя, endpoint, переданные
  параметры, сетевой адрес, код ответа и длительность обработки.
- **FR-026**: Отказ записи в журнал MUST NOT отменять уже выполненную выдачу номера и MUST NOT
  менять тело ответа клиенту.

### Key Entities

- **Проект** — зарегистрированный репозиторий. Несёт нормализованный ключ, выведенный из адреса
  репозитория, человекочитаемое имя, исходный адрес, признак активности и автора регистрации.
- **Тип ключа** — род документа (ADR, спецификация и заведённые позже). Несёт код, имя, шаблон
  форматирования идентификатора и признак активности. Общий для всех проектов.
- **Включение типа в проекте** — связь проекта и типа ключа, несущая состояние нумерации этой пары.
  Существование связи означает, что тип обслуживается в проекте.
- **Выданный идентификатор** — запись реестра: проект, тип, тема документа, порядковый номер, автор
  запроса и момент выдачи. Неизменяема и неудаляема.
- **Пользователь** — сотрудник корпоративного домена. Несёт роль (обычный или администратор) и
  связанные токены доступа.
- **Запись журнала** — обращение к API: пользователь, endpoint, параметры, адрес, код ответа,
  длительность, момент.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: При 50 одновременных запросах номера для одной пары «проект + тип» выдаётся ровно 50
  различных номеров без пропусков, и ни один запрос не завершается ошибкой.
- **SC-002**: Повторный запрос с той же тройкой возвращает тот же номер в 100% случаев, включая
  повтор, отправленный до завершения первого.
- **SC-003**: Запрос по незарегистрированному адресу репозитория в 100% случаев возвращает отказ, в
  теле которого присутствует нормализованный ключ проекта.
- **SC-004**: Разработчик подключает сервис к AI-ассистенту и получает первый номер, не вводя ключ
  проекта руками и не читая документацию дольше одной страницы.
- **SC-005**: Администратор заводит новый репозиторий в справочнике и делает его пригодным для
  выдачи номеров не более чем за три операции.
- **SC-006**: Ни один сценарий эксплуатации не приводит к повторной выдаче ранее выданного номера —
  проверяется регрессионным набором на конкурентность, повтор и вывод сущностей из обращения.

## Assumptions

- Команда работает внутри одной организации, и разграничения доступа между проектами нет: любой
  аутентифицированный сотрудник может запросить номер в любом зарегистрированном проекте, если знает
  его ключ. Скрыт именно перечень проектов, а не данные по известному ключу. Разграничение по
  участию в проекте может быть добавлено позже без слома контракта.
- Адрес origin читает клиент, а не сервис: сервис не имеет и не получает доступа к репозиториям.
- Токен действует бессрочно до отзыва. Срок жизни и ротация не вводятся в первой версии.
- Первый администратор задаётся списком адресов электронной почты в конфигурации развёртывания и
  применяется при первом входе этих пользователей.
- Перечень выданных идентификаторов отдаётся целиком, без разбиения на страницы: ожидаемый объём —
  десятки, реже сотни записей на пару «проект + тип».
- Нагрузка — единицы запросов в минуту. Горизонтальное масштабирование и распределённая выдача
  номеров не проектируются.
- Веб-интерфейс минимален: вход, страница токена и администрирование справочников. Он не является
  продуктом и не проектируется под сторонних пользователей.
- Интеграция в рабочий процесс на стороне потребителя (когда именно агент обращается за номером) —
  вне границ этой спецификации.
